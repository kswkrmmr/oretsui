# 俺についてこい（oretsui）

## 本番環境URL

https://oretsui.vercel.app

スマホのブラウザで開いてください。位置情報の許可が必要です。ホーム画面に追加すると、アプリのように全画面で使えます。

### 主な機能

- 散歩したい時間（または距離）と歩く速さを選ぶだけで、今いる場所から出発して戻ってくる周回ルートを自動で作る
- 「兄貴」キャラクターが地図の上で少し前を歩いて先導し、場面に合わせて声をかける
- 散歩中は現在地を追いかけ、歩いた距離・残りの距離・経過時間を表示する
- ルートから外れたら知らせる（GPS の精度に合わせて判定の厳しさを変える）
- 逆回りに歩き出しても、自動で逆回りとして扱う
- 向いている方角が上になるように地図を回す（北が上と切り替えられる）

## 8. MVPで実現する機能

- 地図をスマホで全画面表示する
- 現在地を出発点にする（使えないときは地図をタップして選ぶ）
- 散歩の条件を選ぶ（時間・距離・歩く速さ）
- 周回ルートを自動で作る
  - 出発点を通る円の上に経由地を3つ置き、徒歩のルートでつなぐ
  - 目標の距離の ±10% に入るまで、円の大きさを調整して最大4回作り直す
- ルートを地図に線で表示し、距離と所要時間を出す
- 別のルートに変える
- 散歩中モード（現在地を追いかけ、歩いた距離と残りの距離を出す）
- PWA 対応（ホーム画面に追加）

## 9. 本リリースで実現した機能

### 兄貴（キャラクター）

- 画面下の吹き出しで、場面に合わせて一言かける（ルートができた、半分来た、あと少し、外れた、おつかれ など）
- 顔の画像は4つの表情（ふつう・笑顔・燃えている・困っている）を場面で使い分ける
- 地図の上で、自分がルート上で歩いた距離の 10m 先を歩いて先導する。止まると待つ

### ルートの向きと逆回り

- ルートの線に、進む向きの矢印を並べる
- 逆向きに歩き出したら、自動で逆回りとして扱う（兄貴が「そっちか！ならこっちだ」と言って回り込む）
  - 出発点から少しの間、行きと帰りで同じ道を通るルートでも働くように、「逆回りの歩いた距離が順回りより 30m 以上多い」かつ「逆回りのルートのほうが近い」で判定する

### ルートから外れたときの知らせ

- GPS の精度に合わせて基準を変える（「精度 + 10m」を 20〜40m に収める）。精度が良いときは、1本隣の道も拾える
- 精度が悪すぎる位置は判定に使わない

### 時間

- 散歩中の経過時間を表示し、終了したら「今日の散歩 ○分・○ km」を出す
- ルートの所要時間は、選んだ歩く速さで計算する（ゆっくり 60・ふつう 80・早歩き 100 m/分）
- ルートの長さが目標の ±10% に入らなかったときは、兄貴が「ちょっと長め／短めになっちまった」と言う

### 地図の向き

- 散歩中は、スマホを向けている方角が上になるように地図を回す。方位磁針のボタンで「北が上」と切り替えられる
- 方角が取れない（許可なし・センサーなし）ときは北を上にして、そのことを知らせる

### そのほか

- 散歩中は画面がスリープしないようにする
- 「出発」「終了」のボタンは、歩きながらでも押しやすいよう横幅いっぱい

## 10. 懸念点と対策

### 懸念点①：GPS の誤差で「外れた」と誤報が出る

対策：

- 外れた位置が2回続いたときだけ知らせる
- GPS の精度（スマホが返す誤差の目安）に合わせて基準を変え、精度が悪すぎる位置は使わない

### 懸念点②：ルートの向きを間違えて歩く

対策：

- ルートの線に矢印を出し、兄貴が少し前を歩いて向きを示す
- 逆に歩き出しても、自動で逆回りとして扱う

### 懸念点③：テストだけでは確かめられない部分がある

GPS・方角のセンサー・実際の道の形に関わる部分は、自動のテストでは確かめきれない。

対策：

- 実際に歩いて確かめるチェックリストを用意し、気になった点を issue にして直す
- 実際に歩いて見つかった道の形（行きと帰りで最初の 20m を共有するルートなど）を、テストに取り込む

## 16. ローカルでの動かし方

### 必要なもの

- Node.js 22 以上
- Google Cloud の API キー（Maps JavaScript API・Routes API）

### 手順

**1. `.env.local` を作成し、以下を設定する**（`.env.example` をコピー）

```
# 地図の表示用（ブラウザで使う）。ウェブサイトの制限をかける
NEXT_PUBLIC_GOOGLE_MAPS_API_KEY=

# 地図の Map ID（ベクター）。未設定なら開発用の DEMO_MAP_ID を使う
NEXT_PUBLIC_GOOGLE_MAPS_MAP_ID=

# ルート検索用（サーバーで使う）。NEXT_PUBLIC_ を付けない
GOOGLE_ROUTES_API_KEY=
```

ブラウザ用とサーバー用でキーを分けています。サーバーからの通信にはウェブサイトの情報が付かないため、ウェブサイトの制限をかけたキーでは Routes API を呼べないからです。

**2. 起動する**

```
npm ci
npm run dev
```

**3. ブラウザで http://localhost:3000 を開く**

スマホの実機で試すときは、同じ Wi-Fi で `npm run dev -- --experimental-https -H 0.0.0.0` として起動し、表示された https の URL を開いてください（位置情報は https でないと使えません）。

### テスト

```
npm run verify     # lint → 型チェック → ユニットテスト → E2E（本番ビルド込み）
npm run test       # ユニットテストだけ
npm run test:e2e   # E2E だけ（初回は npx playwright install webkit chromium）
```

### 補足

- `npm run verify` は E2E の前に本番ビルドを作るため、動いている開発サーバーが壊れることがあります。そのときは `rm -rf .next` してから `npm run dev` で起動し直してください
- テストは Google Maps・Routes API を読み込みません（通信を遮断・モックしています）。API キーがなくても通ります

## 17. ループエンジニアリングによる開発

このアプリは、**ループエンジニアリング**で開発しました。人間が毎回 AI に指示を出すのではなく、AI エージェントが「issue を取る → 実装 → 検証 → レビュー → PR 作成」を自分で繰り返す仕組み（ループ）を設計し、人間はゴール・制約・止まったときの判断を担当します。

### 開発の記録（2026/10/16〜10/22）

| 項目                 | 値                                                          |
| -------------------- | ----------------------------------------------------------- |
| 期間                 | 7日                                                         |
| マージした PR        | 43件                                                        |
| クローズした issue   | 39件                                                        |
| テスト               | ユニット 280件、E2E 約30件（iPhone・Android の2端末で実行） |
| コードとテストの行数 | テストのほうがコードより多い（約1.6倍）                     |

### ループの流れ

```
issue を1つ選ぶ（loop-guard next）
  ↓
ブランチを切る → テストを先に書く → 実装
  ↓
検証（loop-guard verify ＝ npm run verify）── 失敗 → 直して再検証
  ↓
レビュー役（別のコンテキストの AI）が判定 ── FAIL → 直して再検証
  ↓
PR を作成 → CI → 通知
  ↓
人間が確認してマージ（ループは watch-pr で待つ）
  ↓
次の issue へ
```

終了条件に当たったり、仕様の判断が必要になったりしたら、issue に質問を書いて止まり、人間の判断を待ちます。

### ハーネス（ループを支える仕組み）

| 部品        | 場所                                     | 役割                                                                                                                           |
| ----------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| ルール      | `CLAUDE.md`                              | 守ること、完了の定義、終了条件、禁止事項                                                                                       |
| 1周分の手順 | `.claude/skills/loop-iteration/SKILL.md` | `/loop /loop-iteration` で自走させる                                                                                           |
| 見張り役    | `scripts/loop-guard/`                    | 回数・時間・差分の大きさを機械的に数え、終了条件に当たったら止める。次の issue の選択、PR の見張り、停止からの再開もこれで行う |
| レビュー役  | `.claude/agents/reviewer.md`             | 作る役とは別のコンテキストで、完了条件を満たしているか・ズル（テストの削除や期待値の緩和）がないかを厳しく判定する             |
| hooks       | `.claude/hooks/`                         | main への直接 push、force push、`.env` の読み取り、PR のマージなどをブロックする。編集したファイルを自動で整形する             |
| 権限        | `.claude/settings.json`                  | 許可するコマンドと禁止するコマンド                                                                                             |
| CI          | `.github/workflows/ci.yml`               | PR ごとに `npm run verify` を実行する                                                                                          |

### 終了条件（失敗で止める）

回数や時間は AI に数えさせず、見張り役（`loop-guard`）が機械的に判定します。

|     | 条件                                                                     |
| --- | ------------------------------------------------------------------------ |
| A   | 同じエラーが2回続く                                                      |
| B   | 1つの issue で検証の失敗が合計5回                                        |
| C   | 1つの issue に30分以上かかる                                             |
| D   | レビュー役の FAIL が2回続く                                              |
| E   | コードで直せない失敗（API キー不足・クォータ・ネットワーク）→ すぐ止まる |
| F   | CI の失敗が2回                                                           |
| G   | 差分が500行を超える（issue が大きすぎる）                                |

### ラベルによる進め方

| ラベル             | 意味                                       |
| ------------------ | ------------------------------------------ |
| `loop:ready`       | 人間が仕様を確認した。ループが着手してよい |
| `priority:high`    | 先に着手してほしい                         |
| `loop:in-progress` | ループが作業中                             |
| `loop:review`      | PR を作成済み。人間の確認待ち              |
| `loop:stopped`     | ループが止まった。人間の判断待ち           |
| `human-task`       | 人間が担当する作業（ループは着手しない）   |
| `rehearsal`        | ループのリハーサル用                       |

次に着手する issue は `rehearsal` → `priority:high` → それ以外（番号の小さい順）で決まります。

### ループの動かし方

1. issue に仕様と完了条件を書き、`loop:ready` を付ける
2. Claude Code で `/loop /loop-iteration` を実行する
3. ループが作った PR を確認してマージする（ループはマージを検知して次へ進む）
4. ループが止まったら、issue のコメントを読んで判断を書き、`node scripts/loop-guard/cli.mjs resume <番号>` → `/loop /loop-iteration`

### やってみてわかったこと

- **止まるべきところで止まることが、自律ループの価値**だった。止まった場面は、どれも人間の判断が必要な場面だった
  - 仕様の判断（実装前に質問して止まる）
  - レビュー役が見つけた設計の欠陥（逆回りの判定が、隣の筋で誤判定する）
  - AI 自身の思い込み（E2E の原因を2回見誤り、終了条件 A で止まった）
  - 外部の障害（CI がブラウザのインストールで止まり、終了条件 C・F で止まった）
- **作る役と確かめる役を分ける**と効いた。レビュー役は、自分で再現用のスクリプトを書いて誤判定を見つけるなど、実装した AI が見落とした問題を何度も見つけた
- **実際に歩いて確かめることは代えがきかない**。自宅前の道の形（行きと帰りで最初の 20m を共有する）による不具合は、テストを書いた AI が想定していなかった。実機の感想 → issue → ループで直す、のサイクルで改善した
- **リハーサルが効いた**。本番の前にダミーの issue でループを回し、ハーネス自体の欠陥（スキルを呼び出せない、PR の見張りの誤報など）を先に見つけて直した
- ハーネスは一度で完成せず、使いながら育てた（停止と再開の手順、PR の見張り、処理順をラベルで決める方式、CI のコンテナ化など）
